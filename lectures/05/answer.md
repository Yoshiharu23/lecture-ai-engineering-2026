- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  `uv run python -m app.retrieval "LoRA QLoRA 違い"`では、上位5件中に第2回・PDF p.52とp.51を含む関連ページが見つかった。p.52では、元の重みを固定し、行列A・Bだけを学習するLoRAと、本体を4bitに圧縮するQLoRAが確認できた。p.51では両者のPEFT上の位置づけと比較図を確認できた。p.47はRAGや知識追加との比較、p.60・p.61は演習内容であり、用語は似ているがこの質問の直接的な根拠ではないため、検索上位と根拠ページは区別した。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  ベクトル検索では`search_materials({'query': 'LoRA QLoRA 固定 学習'})`が1回、Graphでは`search_graph({'query': 'LoRA 固定 学習 QLoRA 追加'})`が1回呼ばれた。どちらもモデル応答回数は2回であった。Treeでは、最初に`browse_tree({})`で講義一覧を開き、`browse_tree({'node_id': 'lec02-main'})`、`browse_tree({'node_id': 'lec02-main-s045'})`、`browse_tree({'node_id': 'lec02-main-p052'})`の順に目次をたどった。すなわち、講義一覧 → 基盤モデルの仕組み → 選んだモデルを、いつ・どう直すか → LoRAとQLoRAのページである。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  今回の六回の実行では、必要な根拠を取得できなかった明確な失敗や、取得後に回答へ使えなかった例は確認できなかった。検索結果のp.47、p.60、p.61は取得対象に含まれ得たものの、この質問では直接的な根拠として使用しなかった。複数の実験回数が少ないため、方式全体の失敗傾向までは評価できない。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  この質問では正答率が同程度であり、ベクトル検索が入力3,027トークン、時間2.37秒、費用0.001331USDと最も軽かった。したがって、単純な用語確認にはベクトル検索を採用候補とする。ただし同じ資料範囲、同じ温度、複数回のばらつきは揃えていないため、  全方式の優劣を一般化できない。全文投入は範囲が438ページ、その他は214ページであり、比較条件は完全には揃っていない。
- 気づき・疑問：
  根拠ページがp.51〜52に集中する単純な質問では、検索件数を増やすほど回答が改善するとは限らない。時間と費用だけでなく、誤った近接ページを選んでいないか、引用したページが実際に根拠になっているかを確認する必要がある。また、全文投入の入力トークン数はベクトル検索の約38倍であり、資料範囲や取得方式を揃えれば費用差の意味はさらに明確になると考えられる。

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：

- 比較した質問と、固定した条件（モデル・対象資料など）：
  質問は演習と同じ「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」で固定した。モデルは`gemini-3.5-flash-lite`、対象資料は全文投入モードで全9資料・438ページであった。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  変更前（`RAG_TOP_K=5`、全方式の基準となる全文投入）は、時間3.36秒、入力117,025トークン、出力287トークン、応答1回、推定費用0.035825USDであった。回答はLoRAが本体重みを固定してA・Bを学習し、QLoRAが本体を4bit圧縮する点を正しく説明した。

  `RAG_TOP_K=3`へ変更して全文投入モードを再実行したところ、時間11.44秒、入力117,025トークン、出力266トークン、応答1回、推定費用0.035772USDであった。回答の要点と引用ページ（p.51、p.52）は変わらず正しいが、質問に対する直接の回答ではなく考え方のヒントを促す表現が増えた。traceには時間、トークン、費用以外の検索ツール呼び出しや設定反映が記録されなかった。
- 改善した例と、残る失敗・制約：
  通常のベクトル検索経路ではなく全文投入経路であるため、`RAG_TOP_K`を変えても取得ページ数を変えられず、改善例は確認できなかった。回答は正しいが、変更前の3.36秒に対して変更後は11.44秒と遅くなり、結果はツール呼び出しではなくモデル応答のばらつきを含む。変更前後の1回ずつの比較なので統計的な速度差を結論できない。
- 気づき・疑問：
  設定変更の効果を正しく検証するには、`RAG_TOP_K=5`と`RAG_TOP_K=3`を通常のベクトル検索モードで比較し、同じ質問・モデル・資料・回数を揃える必要がある。今回の記録は、設定変更だけでは全文投入経路には影響しない例として有用である。

- 取り組んだレベル：発展
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  ベクトル検索、Graph、関連ページの前後1ページを組み合わせるハイブリッド取得を実装した。
  - `app/retrieval.py`：ベクトル検索とGraphのseed・expanded候補に加え、候補ページと同じ資料内の前後1ページを追加する`search_hybrid()`を実装した。
  - `app/tools.py`：ハイブリッド取得を呼び出す`search_hybrid`ツールを追加した。
  - `app/agent.py`：発展用の指示文と`--hybrid --trace`モードを追加した。
  - `tests/test_build_rag_index.py`：前後ページが候補に追加されることを確認するテストを追加した。

  基本RAGには既存のベクトル検索方式、発展版には`search_hybrid`で得られる入口ページ、グラフ拡張ページ、前後ページを使わせた。設計上の狙いは、コンパクション（p.39付近）とセッションをまたぐメモリ（p.39）、長期メモリへの選別（p.40）が離れたページに分かれていても、前後のページを補って一連の説明を取得しやすくすることである。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  質問：「第3回ではコンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか。」
  モデルは`gemini-3.5-flash-lite`、対象資料は第1〜3回の本講義214ページ、取得方式以外の条件を揃えて比較した。なお、比較は各方式を1回ずつ実行したものである。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  基本RAGでは、検索語をコンパクションとセッションをまたぐメモリの2回に分けて実行した。
  - 回答：コンパクションは同じセッション内で履歴を要約する処理、セッションをまたぐメモリは外の保存先で次回以降に引き継ぐ処理と説明した。日々のメモはすべてではなく、重複除去や繰り返しテーマの基準を通ったものだけ長期メモリに移ると説明した。
  - 根拠：第3回・PDF p.13、p.38、p.39、p.40、p.65。
  - 計測：時間3.64秒、入力4,441トークン、出力517トークン、モデル応答2回、推定費用0.002625USD。
  - trace：`search_materials({'query': 'コンパクション'})`と`search_materials({'query': 'セッションをまたぐメモリ 長期メモリ 日々のメモ'})`を各1回呼んだ。

  発展版ハイブリッドRAGでは、ベクトル検索・Graph・前後ページを組み合わせた。
  - 回答：コンパクションとセッションをまたぐメモリの範囲と役割を明確に分け、日々のメモから基準を超えたものだけが長期メモリへ移る点を説明した。
  - 根拠：第3回・PDF p.39、p.40、p.65を主な根拠として引用した。
  - 計測：時間7.51秒、入力5,342トークン、出力545トークン、モデル応答2回、推定費用0.002965USD。
  - trace：`search_hybrid({'query': 'コンパクション セッション メモリ 長期メモリ 日々のメモ'})`を1回呼んだ。seedには`lec03-main-p039`が含まれた。

- 改善した例と、残る失敗・制約：
